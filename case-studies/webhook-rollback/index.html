Change control

Rolling back a webhook that worked

The pilot delivered events, but its trust settings were too broad. The integration was removed and the unsafe settings were reverted.

By BoublerTechNovember 25, 20262 min read

The operating problem

The pilot connected Git-backed events to workflow automation. Delivery succeeded, but the configuration used a wildcard host allowance and disabled TLS verification. The result exposed a tension that can be easy to miss during integration work: a message arriving at its destination is only one part of success.

The decision and result

The June 30 rollback record says the webhook and associated workflow were deleted and the unsafe service settings were reverted. The source services were checked after rollback. This removed the pilot integration; it was not a removal of either application.

Observation Interpretation
Pilot event delivery worked. The delivery path existed in that test.
Wildcard host allowance and disabled TLS checks were present. The trust boundary was broader than acceptable for the pilot.
Webhook and workflow were removed; settings were reverted. The pilot was rolled back rather than promoted.
Successor design appears in later records. A successor should be judged by its own acceptance evidence, not credited to this rollback.

What this taught the operating process

Integration checks should validate both function and trust: intended source, allowed destination, transport verification, event authentication, and a rollback that actually removes the pilot. This case is a success in change control because a working but unsuitable configuration was stopped and corrected.

Boundary: The reviewed record supports the June rollback. It does not prove that any later replacement was accepted or remains active now.
