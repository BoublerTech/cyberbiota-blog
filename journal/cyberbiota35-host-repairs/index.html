CyberBiota3.5 · Retrospective

Before adding more AI, we had to fix the host

A drifting clock, an authentication crash loop, uncapped containers, and a nearly full system disk became the first jobs in the CyberBiota3.5 upgrade.

Events: November 23–24, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

At the start of the CyberBiota3.5 work, OpenClaw answered its health check while the authenticated route failed with HTTP 502. Authelia was restarting. The host also wasn’t synchronizing its clock.

That was a useful place to begin. Adding a new agent structure wouldn’t repair the service sitting in front of it.

Repair the clock and check the route again

The audit found Chrony trying to reach time sources over NTS, the authenticated time-synchronization protocol, and receiving connection refusals. The approved repair added working NTS sources and stepped the clock. The recorded correction was about 3.5 seconds.

Afterward, the host reported that its clock was synchronized. Authelia became healthy. The reliability check that had received a 502 now received a 401 on the protected route—the expected result for a request without a login. That checked something the gateway’s direct health response couldn’t: the authentication layer was responding again.

Those results support the recorded repair. They don’t establish that every possible Authelia failure comes from clock drift. Here, clock synchronization, authentication health, and the proxy retest were checked together.

Put limits around the workloads already running

Most of the running containers had no CPU or memory limit. We applied measured limits and saved them in ten Compose files, then validated all ten with docker compose config -q.

cAdvisor was the clearest before-and-after example. The first remediation receipt recorded it at 3.39 GiB before recreation and about 50 MiB afterward, with a 512 MiB limit. A later checkpoint showed about 37 MiB. These are snapshots, rather than a long-term memory benchmark, but they explain why the existing footprint needed attention.

At the first checkpoint, all 70 running containers had CPU and memory limits and none were unhealthy. After the later host work, the corresponding count was 71 of 71. Temporary agent sandboxes can change the running count, so those numbers belong to their checkpoints.

We also removed the deprecated Portainer container and 26 stale rehearsal or candidate containers. Dockhand stayed healthy. No volumes were deleted. Portainer’s Compose service was placed behind a deprecated profile, preserving a route back without leaving it running.

Make room without deleting the data

The root SSD had only about 58 GiB available in the initial audit. The project required at least 20% free space on that disk—about 93.6 GiB.

The next stage reclaimed roughly 70.6 GB of unused Docker build cache and 1.7 GB of dangling images. During the power-stability and storage work, Docker and containerd storage were moved onto the larger data SSD. The post-move record verified the bind mounts and showed the root disk at 70% used, with about 137 GiB free.

The same checkpoint recorded the battery charge cap at 80%, synchronized time after reboot, healthy Authelia and cAdvisor, and no failed system or user units. It gave us a working baseline for continuing the upgrade. It didn’t prove the cause of every earlier freeze, so the project kept a seven-day observation period for stability.

Fix the backup job too

The repository backup had been exiting with status 3. The repair added narrow exclusions for protected key, runtime, and staging paths instead of loosening their permissions. The rerun completed successfully, and restic check passed across the 44 existing snapshots. Nothing was pruned.

By the end of this stage, the lab had synchronized time, a working authentication check, bounded containers, more system-disk headroom, and a passing repository backup. The new AI work could now be tested against that baseline.
