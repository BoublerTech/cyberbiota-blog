A drifting clock and a crowded SSD

The CyberBiota3.5 work began with a broken authentication route, uncapped containers, and a system disk that needed attention.

By BoublerTechNovember 25, 20263 min read

When I started the CyberBiota3.5 upgrade, OpenClaw’s health endpoint answered while the protected route returned HTTP 502. Authelia, the service handling authentication, was stuck restarting. The machine underneath it also wasn’t synchronizing its clock.

There were already 70 containers running on the laptop. Before adding the new agent roles, I approved a round of repairs to the host and the services it was already carrying.

The clock repair changed the authentication result

The time-service logs showed Chrony trying to reach NTS sources and receiving connection refusals. NTS adds authentication to network time synchronization. The approved repair added working sources and stepped the clock by about 3.5 seconds.

The next checks showed a synchronized clock and a healthy Authelia container. The protected-route test changed from 502 to 401. For that request, 401 was the expected result: the client hadn’t logged in, and the authentication layer was now answering.

Checking OpenClaw directly hadn’t exposed that difference. Its process could be alive while the login route in front of it was broken. I kept the proxy test alongside the direct health check.

The repair record supports that sequence for this fault. It doesn’t settle the cause of every earlier authentication problem or host freeze.

cAdvisor was using more than three gigabytes

The audit found no memory limit on 53 of the 70 running containers and no CPU limit on 55. The remediation set measured limits, saved the settings in ten Compose files, and ran docker compose config -q against each file.

cAdvisor gave the clearest before-and-after reading. Its recorded usage was 3.39 GiB before recreation. Afterward it was about 50 MiB, with a 512 MiB limit; a later checkpoint showed about 37 MiB. Those are individual readings rather than a long-term benchmark, but they made the resource problem concrete.

At the first completed checkpoint, all 70 running containers had both limits and none were unhealthy. The later post-reboot count was 71 of 71. The running total changes when a temporary agent sandbox is present, so I attach those counts to the checks that produced them.

I also approved removing the deprecated Portainer container and 26 stale rehearsal or candidate containers. Dockhand stayed healthy. No volumes were removed, and Portainer’s Compose definition remained available behind a deprecated profile.

Make room on the disk that needed it

The smaller system SSD was 87% full at the initial audit, with about 58 GiB available. The project required at least 20% free space on that disk, roughly 93.6 GiB. The larger data SSD still had about 1.2 TiB available.

The next stage reclaimed approximately 70.6 GB of unused Docker build cache and 1.7 GB of dangling images. During the power and storage work, Docker and containerd storage moved onto the larger SSD. The post-move checks verified the bind mounts and found about 137 GiB free on the system disk, now 70% used.

The same checkpoint showed the battery charge cap at 80%, synchronized time after reboot, and healthy Authelia and cAdvisor. It gave me a baseline to continue from. The earlier stability problems still needed observation over several days.

Keep the old backups

The repository backup job had been exiting with status 3. Its repair added narrow exclusions for protected key, runtime, and staging paths. File permissions stayed restricted.

The rerun succeeded, and restic check passed across all 44 existing snapshots. Nothing was pruned. Between the clock repair, resource limits, storage work, and passing backup, the next stage had a much clearer starting point than the first audit did.
