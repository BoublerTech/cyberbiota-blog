AriseOne and the first repeatable jobs

Running a file service came with a new job: looking after the machines running it. Here is what the early health check, Ansible playbook and ticket system actually did.

Events: January to February 8, 2026Evidence: January repository records and a February retrospectiveEntry date: November 24, 2026

The first thing I wanted AriseOne to do was simple: give me somewhere at home to run my own apps and keep my own data. I wanted to do it with open-source tools. Running several services made the next question obvious. How was I supposed to keep track of what each machine needed?

A script that started with a ping

The early repository has a Bash health check. It starts with a fixed list of machines. For each one, it tries a ping and then attempts to collect information like system load and free memory over SSH. The script can produce JSON as well as text. That made it possible to look at more than one machine from the same place.

The script still had a boundary. A reply to a ping didn’t tell me whether a file service was usable. It told me a machine had replied. SSH and the commands run through it were a second test, and the application would need another. That distinction shows up again later in the story, when Grafana can connect to a database but has nothing useful to display.

The Ansible playbook handled a different job. It refreshed the package cache on Debian-family systems, applied upgrades, and cleaned unused packages. At the end it looked for the reboot-required marker and reported which host needed attention. It didn’t reboot the machines. I could see where the automation stopped and where somebody still had to make a decision. These are things I can see in the January repository. I don’t have a run record that shows how often the playbook was used.

A lab with more than one job

The early February account describes the services that gave AriseOne a daily purpose. Nextcloud was the file service. Homepage was a single place to find the services. Zammad was for tickets. Proxmox ran the virtualized pieces, and a recurring problem with NVIDIA drivers turned up when the kernel changed. The notes describe a repair script and a ticket trigger. They don’t give me a full run showing that a ticket could trigger and verify a repair by itself.

The February 7 and 8 notes describe checking Zammad before changing a system and moving Markdown notes into its knowledge base. That was a way to put the past work somewhere it could be found the next time a driver or service broke. It matters here because I was learning how much of running the lab depended on having useful notes about it.

The dates in the archive don’t all mean the same thing. A later account puts the workspace setup on January 16, and the earliest repository entries I’ve reviewed are from January 20. The next build has its own log. It shows the ideas I kept working with, including Proxmox, monitoring and ticketing. It leaves open which individual services and data moved over.
