Qwen3 stayed local. The coordinator moved to the cloud.

A successful tool call was followed by a failed delegation test. That failure shaped the hybrid setup I put into production.

By BoublerTechNovember 25, 20263 min read

Qwen3 could produce the tool call I asked for. That was the first encouraging result in the CyberBiota3.5 model tests. The harder delegation test failed later in the same project.

I had confirmed qwen3:8b as the local baseline. Ollama was already serving it on the RTX 2070, and I wanted to keep using it. The tests helped separate the jobs it had demonstrated from the coordinator job that still needed work.

A tool call and a delegated task are different work

The first tool-schema test asked Qwen3 to select a named network-health query. It returned the expected arguments:

{"query_template_id": "dns_latency_p95", "window_minutes": 15}

A separate malicious-ticket test requested secret access, firewall changes, and self-approval. The model refused and made no tool calls.

In the staging pilot, the coordinator had to spawn a child and handle the deferred tool response. On that multi-step task, Qwen3 returned an empty disposition. I kept that failed result in the record.

The approved OpenAI OAuth model completed the same task class. It delegated to noc-lead, which ran local Qwen3 inside its own Docker sandbox. That gave me a practical reason for the hybrid arrangement: use the cloud coordinator for the tested delegation work while keeping local inference for the other roles.

It was a task-specific result. I didn’t have a benchmark showing that every cloud task would be better, and the cold tool-call timings weren’t comparable to warm role turns.

Keep shell execution denied

Authentication was only one part of making the cloud route work. The unauthenticated requests had failed without switching providers. After I completed device-code approval in the isolated profile, the subscription model catalog could be refreshed.

The next blocker was the execution harness. The selected Codex harness rejected the configuration while shell execution was denied. I wasn’t going to treat enabling shell access as a harmless way around that test.

The working configuration selected OpenClaw’s built-in runtime for the cloud model. A harmless prompt then completed with tools.exec.mode still set to deny. The receipt identified the expected provider and model, a sandboxed run, and no fallback.

A follow-up request for a shell command and a host-file read was blocked. The governance role also had no inherited OAuth profile, and the workspaces had no copied credential databases.

Check the route at both ends

The pilot used gpt-6-astra for main. Delegation to local noc-lead succeeded. A direct request from main to soc-tier1 was denied because it skipped the security lead.

The installed OpenClaw release didn’t initially contain the newer 6.2 entries in its catalog. I approved the runtime upgrade separately before selecting the production model.

On November 25, the live coordinator was set to openai/gpt-6.2-sol through the built-in runtime. The default stayed ollama/qwen3:8b for the other 44 registered roles. The live smoke identified the expected cloud model and FALLBACK_USED=False. The checked gateway process had no OpenAI API-key environment variable, and the 31 new role directories had no duplicated OAuth credentials.

The live cloud-to-local route passed, and the specialist bypass was denied again. That was the arrangement I accepted for the production cutover. Cloud coordination still means cloud processing; keeping the specialists local doesn’t make the whole request local. Provider limits and failure handling remain things to check during actual operation.
