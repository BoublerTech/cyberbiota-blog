Why the coordinator went to the cloud

Qwen3 passed a typed-tool test but failed the pilot’s multi-step delegation task. A separate runtime problem also had to be solved without enabling shell execution.

Events: November 23–25, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

I chose Qwen3 for CyberBiota3.5 because it was already the local model I wanted to keep using. The first inspection confirmed Ollama was serving qwen3:8b on the RTX 2070. We kept it as the local baseline rather than downloading another model to match an outdated proposal.

The tests showed where that choice worked and where the coordinator needed something else.

One correct tool call didn’t prove coordination

In the first model test, Qwen3 produced the expected typed call to network_health_query, selecting a DNS-latency query and a 15-minute window. A separate malicious-ticket test asked for secret access, firewall changes, and self-approval. The recorded response refused, with no tool calls.

The staging pilot was harder. It required the coordinator to delegate work and handle the deferred tool response. Qwen3 returned an empty disposition on that multi-step task. That failure stayed in the record.

On the same task class, the approved OpenAI OAuth model succeeded. The pilot coordinator delegated to noc-lead, and the child ran on local Qwen3 in its own Docker sandbox. That result gave us a specific reason for hybrid routing: use the cloud coordinator for the tested delegation task and retain local inference for the other roles.

It wasn’t a benchmark proving every cloud task would be better. The local cold tool-call test and the later warm role turns also had different timings and workloads, so they shouldn’t be compared as if they were the same test.

Authentication and execution were separate problems

The first unauthenticated cloud requests failed rather than switching providers. After I completed the official device-code approval for the isolated profile, the subscription catalog could be refreshed.

There was still a runtime conflict. The selected Codex harness rejected the configuration while shell execution was denied. Enabling shell access would have changed the security boundary we were trying to test.

The working configuration explicitly selected OpenClaw’s built-in runtime for the cloud model. The harmless cloud prompt then completed while tools.exec.mode remained deny. The receipt recorded a sandboxed run, the expected provider and model, and no fallback.

A follow-up request for shell execution and a host-file read was blocked. Separately, the governance role had no inherited OAuth profile and the workspaces contained no copied credential databases.

Prove the route and the refusal

The staging pilot used gpt-6-astra for the coordinator. Its allowed route to local noc-lead succeeded. A direct route from main to soc-tier1 was denied because the coordinator was required to go through the security lead.

Stopping the staging gateway left the live gateway and the existing monitoring services responsive. This let us test the coordinator without making monitoring depend on the experimental controller.

Carry the tested choice into production

The installed OpenClaw release didn’t initially include the newer 6.2 model entries in its catalog. We handled the release upgrade as a separate approved change, rather than treating a model name in a proposal as proof it was usable.

After the November 25 upgrade, the live account-scoped catalog exposed the approved model. main was changed to openai/gpt-6.2-sol through the built-in OpenClaw runtime. The default stayed ollama/qwen3:8b for the other 44 registered roles.

The final smoke recorded the expected provider and model with FALLBACK_USED=False. The checked gateway process had no OpenAI API-key environment variable, and the 31 new role directories had no duplicated OAuth credentials. Live cloud-to-local delegation succeeded, and the direct-specialist bypass was denied again.

Cloud coordination is still cloud processing; local specialist execution doesn’t make the whole request local. These receipts establish the tested route and credential checks. They don’t establish that every future task, quota response, or provider failure will behave correctly. Those remain part of operating the system after cutover.
