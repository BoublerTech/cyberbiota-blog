What happened when I tested the incident teams

Five controlled scenarios tested delegation, duplicate handling, and approval checks while production changes stayed disabled.

By BoublerTechNovember 25, 20263 min read

A retry should not create another incident team and another pile of tickets. That was one of the behaviors I wanted checked before accepting the CyberBiota3.5 operations work.

After the individual adapters were passing, the project exercised five controlled scenarios. The scenario inputs were synthetic. Some checks read the live lab, but the tests didn’t break production or pretend that a sample security event was a real compromise.

Follow the smallest useful route

The database-slowdown scenario followed main → dba-lead → dba-performance and read live connection and lock statistics. The DNS scenario used the network lead, the service specialist, a DNS check, and the monitoring probe summary.

For a suspicious endpoint event, the test combined security posture, a benign forensic manifest, and an offline detection sample. It produced a draft case and a proposed response with execution still false.

The OpenClaw-failure scenario checked monitoring evidence that existed independently of the AI controller. The storage-pressure scenario read disk and backup coverage, then drafted a request. It didn’t prune backups or delete volumes.

These were Python orchestration tests. The separate staging pilot and production smoke supplied the live model-delegation evidence. I wasn’t counting the five scenarios as five autonomous teams that had repaired the host.

Replay the work

Each scenario was run again with the same identifier. The tickets, cases, and change requests were deduplicated instead of being created twice.

The retry and tool budgets were tested separately. A flaky backend hit its circuit breaker after the initial request and two retries. A two-call tool budget refused the third call. Configuring three concurrent runs was rejected; the exercised modes were serial execution or at most two total runs.

Those limits fit the machine. A failing backend shouldn’t turn into an expanding queue of local inference jobs on one GPU.

Try the wrong action through the right route

The orchestrator loaded its allowed delegation edges from the candidate manifest. Tests rejected recursive routes, cross-department jumps, a coordinator skipping a lead, and a specialist spawning another worker.

A valid route also had to refuse prohibited work. The negative tests sent requests for shell execution, live IP blocking, volume deletion, backup pruning, container management, and self-approval through otherwise valid coordinator-to-lead-to-specialist chains. They were denied.

The approval verifier ran outside the language model. It checked the human approver, permitted target and operation, canonical packet digest, signature, expiry, and a single-use nonce. Tests rejected changed parameters, a forged signature, expired approval, replay, and agent identities used as approvers.

Even the correctly signed test packet stayed in dry-run mode. Production execution remained disabled.

Read the passing result in context

The combined Python suite reached 37 passing tests across monitoring, security, inventory, databases, service desk, and incident orchestration. The useful part was the behavior behind that number: bounded queries, repeat handling, refusals, and a verifier that didn’t let the model grant itself approval.

It was still a finite test suite. I accepted that tested scope and left the production executor disabled for the live role and coordinator cutover.
