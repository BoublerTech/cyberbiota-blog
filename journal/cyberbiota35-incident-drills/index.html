CyberBiota3.5 · Retrospective

Five incident drills, with production changes disabled

We exercised small incident teams, duplicate handling, forbidden actions, and an approval verifier that stayed outside the model—and in dry-run mode.

Events: November 24, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

Once the individual adapters were passing, we needed to see what happened when a problem involved more than one role. For CyberBiota3.5, we used five synthetic incident drills.

The scenarios were invented test inputs. Some read-only checks reached the live lab, but we didn’t break production to make the stories more realistic, and no drill was an actual security incident.

Assemble only the team the scenario needs

A database slowdown followed the route from main to dba-lead to dba-performance, then read live connection and lock statistics. A DNS outage used the network lead, the service specialist, a DNS check, and the monitoring probe summary.

The endpoint-event drill combined security posture, a benign forensic manifest, and an offline detection sample. Its output was a draft case and a proposed response, with execution still false.

The OpenClaw-failure drill checked whether the existing monitoring evidence remained available independently of the AI controller. The storage-pressure drill read disk and backup coverage and produced a draft request. It didn’t prune backups or delete volumes.

The Python orchestrator loaded delegation edges from the candidate manifest. Tests rejected recursive delegation, cross-department jumps, a coordinator skipping directly to a specialist, and specialists trying to spawn another worker.

These were controlled orchestration tests. The separate live gateway pilot and production smoke supplied the model-delegation evidence; the five drills weren’t five autonomous live model teams repairing the host.

Repeat the request and limit the retries

Each scenario was replayed with the same run identifier. Tickets, cases, and change requests were deduplicated instead of creating another set of records.

The runner also imposed budgets. A flaky backend hit its circuit breaker after three attempts: the initial request and two retries. A test with a two-call tool budget refused the third call. Configuring three concurrent runs was rejected; the exercised limits were serial execution or at most two total runs.

That mattered on a laptop with one local GPU. A failed backend shouldn’t create an expanding queue of reasoning jobs.

A valid delegation path can’t authorize a forbidden action

The negative tests sent prohibited requests through otherwise valid coordinator-to-lead-to-specialist chains. Shell execution, live IP blocking, volume deletion, backup pruning, container management, and self-approval were refused.

The approval component had its own checks outside the language model. It compared the human approver, allowed target and operation, canonical change-packet digest, signature, expiry, and single-use nonce. Tests rejected altered parameters, a forged signature, expired approval, replay, and attempts to use an agent identity as the approver.

Even the correctly signed test packet remained in dry-run mode. The verifier did not grant a production executor permission to act.

What the passing suite meant

By this point the combined Python suite contained 37 passing tests across monitoring, security, inventory, databases, service desk, and incident orchestration.

That result was useful because it included refusals and failure handling, not just successful queries. It was still a finite test suite. It didn’t independently certify the security of every interface or establish a working production remediation service.

The production executor remained disabled. The next stage could register the roles and test the live coordinator without quietly turning these draft workflows into autonomous host administration.
