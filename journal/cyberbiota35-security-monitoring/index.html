CyberBiota3.5 · Retrospective

Building security visibility that fit the laptop

The security work used existing signals and bounded investigations. The RAM calculation kept Wazuh out, and offline detection samples stayed clearly labeled.

Events: November 23–24, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

Wazuh was part of the CyberBiota3.5 proposal. The machine’s resource budget decided whether it belonged in this implementation.

At the admission checkpoint, the Dell had about 12.2 GiB of available RAM. The project’s budget for the proposed Wazuh central stack was 8 GiB. Subtracting that left roughly 4.2 GiB—below the 8 GiB safety reserve and below the 6 GiB stop threshold.

We deferred it. The disk work had made room for files, but it hadn’t added RAM.

Use the security signals already present

CrowdSec and Alertmanager were running. The new security adapter queried their existing signals without enabling active response. Requests for Wazuh data returned a structured unavailable result because there was no Wazuh backend to query.

The vulnerability adapter read stored reports. It didn’t trigger an active scan. Case creation produced a draft, and the response interface produced a proposal awaiting approval, with executed: false.

Those distinctions mattered on a home lab carrying my apps and data. A security-related message was still data to inspect, not permission to change the firewall or stop a container.

The first security test set included malicious instructions embedded in tickets, cross-role access attempts, and input filtering for indicator lookups. Internal addresses, internal domains, and incident prose were rejected as external-enrichment inputs. The evidence here includes offline indicator fixtures; it doesn’t prove a complete live threat-intelligence service.

Test detection logic without claiming a sensor

We used benign positive and negative controls for detection handling. A matching sample had to appear, and a nonmatching control had to stay absent.

Later tests parsed offline EVE JSON and Zeek connection samples. The EVE test removed two raw-payload fields before returning a result. Connection summaries exposed metadata rather than packet contents.

Suricata wasn’t installed, and there was no switch-mirror feed. Passing these tests showed that the adapter handled those samples. It didn’t establish live network intrusion detection.

The live socket query had a different, narrower source: passive sockets on the Dell itself. Its result explicitly described local-host coverage. It couldn’t see all traffic crossing the home network, and we didn’t label it as if it could.

Inspect the endpoint without handing over a shell

The endpoint posture view gathered a fixed selection of information such as AppArmor status, failed units, and the state of existing security services. The investigation adapter used pre-approved packs for listening ports, container digests, privileged containers, and systemd timers.

The live container review still found two privileged containers and seven using host networking. The new agent sandboxes didn’t remove those existing exceptions. Keeping the exceptions in the record prevents a successful sandbox test from turning into a claim that the whole Docker estate has the same isolation.

Forensic handling was tested with a benign collection manifest and SHA-256 verification. The result returned evidence metadata rather than raw contents. That was a controlled test of the metadata path, not an investigation of an actual compromise.

What remained outside this upgrade

We also deferred Security Onion, Arkime, Graylog, Greenbone/OpenVAS, MISP, Fleet, Velociraptor, and Shuffle. Some would need substantially more resources; others would need a separate justification, target scope, or execution authorization.

The delivered work was smaller and more specific: existing security-signal queries, draft cases, bounded posture and investigation helpers, and tests that distinguished live data from offline samples. CyberBiota3.5 did not become a complete SIEM or an autonomous response platform during these three days.
