Why I left Wazuh out of this build

The laptop had room for bounded security queries. The RAM budget ruled out the proposed central SIEM stack.

By BoublerTechNovember 25, 20263 min read

Wazuh was in the CyberBiota3.5 proposal, but the laptop’s RAM budget ruled it out of this build.

At the admission checkpoint, about 12.2 GiB of RAM was available. The project’s allowance for the proposed Wazuh central stack was 8 GiB. That would leave roughly 4.2 GiB, below both the 8 GiB safety reserve and the 6 GiB stop threshold.

I deferred the stack. Moving Docker storage had made room on disk; it hadn’t added memory.

Start with the signals already available

CrowdSec and Alertmanager were already running. The new security helper queried their existing signals without enabling active response. Asking for Wazuh data returned an unavailable result because there was no Wazuh backend to query.

The vulnerability helper read stored reports rather than starting a scan. Case creation produced a draft. The response interface produced a proposal awaiting approval, with executed: false.

The tests included malicious instructions embedded in tickets, cross-role access attempts, and filtering for indicator lookups. Internal addresses, internal domains, and incident prose were rejected as external-enrichment inputs. The indicator tests used offline fixtures, so I wasn’t treating them as proof of a complete live threat-intelligence service.

Use a sample without calling it a sensor

The detection tests used benign positive and negative controls. A known matching sample had to produce a result, while a nonmatching control had to stay absent.

Later checks parsed offline EVE JSON and Zeek connection samples. The EVE test removed two raw-payload fields before returning its result. The connection summaries returned metadata instead of packet contents.

Suricata wasn’t installed, and the host had no switch-mirror feed. These tests established how the helpers handled those samples. They didn’t establish live intrusion detection across my network.

The live connection source was narrower: passive sockets on the Dell itself. Its result labeled that local-host coverage explicitly. It couldn’t see everything crossing the home network.

Inspect the host through fixed questions

The endpoint posture view collected a defined selection of information, including AppArmor status, failed units, and existing security-service status. The investigation helper used pre-approved packs for listening ports, container digests, privileged containers, and systemd timers.

The container review found two privileged containers and seven using host networking. Those were existing exceptions in the lab. Adding restricted agent sandboxes didn’t remove them, and a passing sandbox test couldn’t describe the whole Docker estate.

A benign forensic collection manifest supplied the chain-of-custody test. SHA-256 verification passed, and the helper returned evidence metadata instead of raw contents. That was a controlled test of evidence handling; there hadn’t been an actual compromise to investigate in that exercise.

Leave the larger additions for a justified change

Security Onion, Arkime, Graylog, Greenbone/OpenVAS, MISP, Fleet, Velociraptor, and Shuffle also stayed deferred. The resource cost, source coverage, target scope, or need for a separate authorization wasn’t resolved by putting a product name in the plan.

The delivered security work was smaller: queries over existing signals, draft cases, fixed posture and investigation helpers, and tests that kept live data separate from offline samples. That gave me specific functions to evaluate during use while the heavier platforms remained outside the approved footprint.
