Storage & recovery

The first backup I could show how to restore

Restic brought selected project files back into a separate folder. The next check was whether the backup would run on schedule.

By BoublerTechNovember 24, 2026Updated November 25, 20262 min read

Work covered: June 25 to July 6, 2026

The first CyberBiota3 recovery exercise started with the project repository. Could I recover the files that explained how the lab was built, without overwriting the working copy?

Restic made an encrypted local backup of the selected repository material, including project instructions and change records. Known sensitive configuration and live runtime data were excluded. Application databases were outside this exercise.

Restore into a separate folder

On June 25, the test confirmed a snapshot existed, then restored it into a separate directory. The README, operations instructions, and backup plan were among the files checked. A separate check looked for paths that were supposed to stay excluded.

Restoring beside the working repository let the test inspect the copy without replacing the files in use. The result was a recovery of selected project files, not just a successful backup command.

Wait for the schedule

On July 6, the systemd timer ran the repository backup without a manual start. It exited with status zero, produced a new snapshot, and passed the Restic check.

The June restore and July run checked different parts of the job. The restore put files back. The timer showed that the scheduled path could create another copy on its own.

The backup was still local. Losing the laptop and its storage together would also mean losing that copy, and neither test restored a running application or database. Later, the CyberBiota3.5 work added an external USB copy and an isolated database restore. Those addressed parts of recovery this first repository exercise had left open.
