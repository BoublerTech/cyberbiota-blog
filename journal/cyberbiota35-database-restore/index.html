Storage & recovery

Restoring a database from the daily backup

I restored the orchestration database into an isolated PostgreSQL instance and checked the tables, indexes, and remaining gaps.

By BoublerTechNovember 25, 20263 min read

The earlier backup checks in the CyberBiota3.5 project could extract files and verify their hashes. The OpenClaw archive also passed a listing check that found PostgreSQL table objects.

The next test needed a running engine. I approved restoring the orchestration dump from the daily backup into an isolated PostgreSQL instance, then checking what the database actually contained.

Check the load before adding another component

The audit had found five PostgreSQL instances, plus MariaDB and Redis or Valkey services. The database helpers read defined statistics for connections, locks, sizes, cache-related views, and persistence. Those operational questions didn’t require application rows.

At the checkpoint, PostgreSQL connection use was between 6% and 12%, with no waiting locks. I left PgBouncer out of this upgrade because those readings didn’t justify a connection pool.

Recovery coverage was less complete. All five PostgreSQL instances had WAL archiving disabled, leaving no demonstrated point-in-time recovery through that mechanism. The records also lacked verified standalone daily dump timers for Gitea, Planka, and Immich. Those gaps stayed on the list.

Start an engine that can’t reach production

The test used the orchestration dump from the verified daily OpenClaw archive. It was extracted into private staging and checked against its SHA-256 checksum.

The temporary PostgreSQL 17 container had no network, no production mounts, a 512 MiB memory limit, and one CPU. No application jobs or webhooks were attached to it. That kept the restored database from accidentally becoming another active copy of an automation service.

The restore ran through pg_restore, followed by ANALYZE. Metadata queries then checked the result without printing user rows:

Restored object Result
Public tables 17
Indexes 40
Populated tables 12
Database size 51 MB

The measured sequence—extraction, checksum, engine startup, restore, and analysis—took 9.48 seconds. The source archive came from midnight local time that day. Those figures describe this one database exercise and its recovery point, rather than the recovery time for all of CyberBiota.

The temporary container and staging files were removed afterward. Production volumes, backup cadence, and retention stayed in place.

Keep a person at the end of the ticket

This phase also added draft service-desk classification, reviewed knowledge drafts, and a closure check requiring a human identifier and evidence references. The tests rejected registered agent IDs used as the human closer.

That checked adapter behavior under the tested inputs. It didn’t establish a complete deployed help-desk identity system. GLPI stayed deferred: Leantime and Planka were already in the lab, and the draft helpers didn’t create a need for another application stack.

A recovery receipt for one database

The restored tables were queryable, the indexes existed, and 12 tables were populated. I now had a functional database restore result to go with the earlier archive checks.

The application itself hadn’t been exercised against that copy. The photo library and the rest of the host hadn’t been recovered either. The runbook retained the missing dump coverage and WAL work as separate jobs, along with a schema-compatibility check before any future image rollback.

This was the orchestration database’s recovery receipt. The other applications still need their own tests.
