A backup archive finally became a running database

The database stage restored a real PostgreSQL dump into an isolated engine, checked tables and indexes, and kept the untested recovery gaps on the list.

Events: November 24, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

Earlier in the CyberBiota3.5 work, we had extracted backup files and checked their hashes. The OpenClaw archive also passed a listing check that found PostgreSQL table objects.

The next stage went further. Could a dump from the daily backup actually restore into a running database?

Start with the database footprint

The audit had found five PostgreSQL instances, plus MariaDB and Redis or Valkey services. The new database adapters exposed fixed statistics: connections, locks, sizes, cache-related views, and persistence status. They didn’t need application rows to answer those operational questions.

At the measured checkpoint, PostgreSQL connection use was between 6% and 12%, with no waiting locks. That didn’t justify adding PgBouncer during this upgrade. We deferred it rather than adding a connection pool without a measured need.

Backup coverage needed more work. All five PostgreSQL instances had WAL archiving disabled, so the project had no demonstrated point-in-time recovery through that mechanism. The records also lacked verified standalone daily dump timers for Gitea, Planka, and Immich. A passing backup elsewhere couldn’t cover those gaps by implication.

Restore without touching production

The functional restore used the orchestration dump from the verified daily OpenClaw archive. We extracted it into private staging, checked its SHA-256 checksum, and started an ephemeral PostgreSQL 17 container.

The container had no network, a 512 MiB memory limit, one CPU, and no production mounts. No application jobs or webhooks were attached. That kept the test database from becoming an accidental second copy of an active automation service.

The dump was restored with pg_restore, followed by ANALYZE. The checks then queried database metadata rather than printing user data.

The recorded result was:

Check Restored result
Public tables 17
Indexes 40
Populated tables 12
Database size 51 MB
Extract, checksum, startup, restore, and analysis 9.48 seconds

The source backup was taken at midnight local time that day. That timestamp identifies the recoverable snapshot used in this exercise. The 9.48 seconds measures this isolated database test; it isn’t a recovery target for the entire home lab.

The temporary container and staging files were removed after the checks. Existing backup jobs, retention settings, and production volumes were preserved.

Put recovery evidence beside the ticket

This phase also added draft service-desk classification, reviewed knowledge drafts, and a closure check requiring a human identifier and evidence references. Tests rejected the registered agent IDs when they tried to stand in for the human closer.

Those were adapter tests. They showed the intended draft and closure behavior under the tested inputs, rather than proving a deployed help-desk identity system. GLPI stayed deferred because the lab already had Leantime and Planka and the new draft helpers didn’t justify another application stack.

Keep the successful restore in its proper scope

The restored database was queryable, its indexes existed, and populated tables were present. That was stronger evidence than merely listing objects inside the dump.

It still didn’t test the application against the restored database, recover the photo library, or bring the whole machine back on replacement hardware. The recovery runbook therefore retained the missing dump coverage and WAL work as separate jobs. It also called out schema compatibility before any future image rollback: reverting an application image doesn’t by itself reverse its database migrations.

This test gave the orchestration database a concrete recovery receipt. The other applications still need their own.
