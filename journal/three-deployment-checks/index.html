A valid Compose file and a failed deployment

Image pulls, application startup, and the route test each exposed something different during the deployment.

By BoublerTechNovember 24, 20262 min read

I had a Compose file that passed validation and a stack that wouldn’t start. The first June 26 attempt stopped at the image pull. Two tags in the definition didn’t resolve at their registries. That left me with a perfectly readable file and software Docker couldn’t fetch.

I could check the image problem on its own. The remediation record shows the replacement tags were inspected against the registry before the next attempt. The new image names fixed that part of the deployment. They also let the apps get far enough to report problems that had nothing to do with tags.

Two apps, two different faults

Infisical was stuck restarting. The inputs it needed were supplied, but their lengths or encoding did not match what the app expected. The repair corrected the inputs and recreated the Infisical app container. Postgres and Redis were left running. The follow-up inspection showed the app running without a restart in that check. Its selected route also returned HTTP 200.

Homarr had a different problem. It returned HTTP 500 because the container was missing an encryption key that the Compose service should have passed in. Adding the mapping and recreating Homarr changed the response to HTTP 307. That sent the browser to first-run setup.

Check Result at the end of the retry
Caddy, Gitea, Infisical and n8n routes The four selected routes responded with HTTP 200.
Homarr route HTTP 307 to the setup screen, after the earlier HTTP 500.
Complete Homarr setup No completed user test in this result.

The point where I stopped for each service tells me what to try next. I would check the tags before the pull, confirm the app can start with the right configuration, and then do the thing I installed the app for. For Homarr, the next check was somebody getting through setup.

Recreating the whole stack would have made this harder to read. The evidence pointed to two apps. Keeping the database and cache in place limited what changed between checks. That’s the part I would carry into another deploy, even if the next stack used completely different software.
