Getting a backup off the host—and restoring from it

We added an encrypted repository to an existing USB drive, checked restored files, and verified the overnight backup job.

Events: November 23–25, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

The first CyberBiota3.5 audit found several successful backup jobs. It also found that the verified copies were on the same Dell that ran the lab.

A local backup could help with a bad configuration or a damaged file. It didn’t give me a verified recovery copy outside the host. We kept that gap open while preparing the upgrade, then added an encrypted Restic repository on the external USB drive, under the name CyberBiota_Ark.

Preserve the drive’s existing files

The USB drive already contained my files. The approved work created a new backup repository in its own directory. It didn’t format the drive or remove what was there.

The backup covered the new 3.5 project records, selected Compose configuration, scripts, and the latest verified daily OpenClaw backup archive. Staging directories and selected sensitive or runtime files were excluded. That scope matters: this was not a complete image of the machine or a backup of every application’s data.

Restic encrypted the repository. The job obtained its credentials through the established secret-management arrangement without writing values into its receipts. The remaining recovery requirement was to keep a usable copy of the repository password outside the Dell. Losing the host must not also mean losing the only way to decrypt the external copy.

The disconnected-drive test came first

During the power and SSD work, the USB drive was disconnected. The backup script was tested in that state and returned its designated skip code without writing into the root filesystem.

That guard prevents a particular failure: a missing external mount can otherwise leave an ordinary directory at the expected path, allowing a job to fill the internal disk while appearing to write to USB. The service checked both the mountpoint and the expected backup directory before proceeding.

After the drive was reconnected, the first recorded run processed about 355 MiB across 13,015 files. It exited successfully, and restic check reported no errors. Starting the service separately also succeeded under its memory and CPU limits.

Bring files back from the external copy

We then restored two selected project files from the USB repository into a private staging directory on the data SSD. Their SHA-256 hashes matched the originals. The measured selective restore took 1.07 seconds, and the temporary directory was removed after verification.

That is a small but concrete test. The files came from the external repository, decrypted, and matched. The 1.07-second figure is the time for those selected files. It is not the recovery time for CyberBiota, its databases, or replacement hardware.

The separate database exercise later in this series went further: it started an isolated PostgreSQL instance and restored a database into it. Each test answered a different recovery question.

Check an unattended run as well

The USB job was scheduled for 04:15, with up to two minutes of randomized delay and a persistent systemd timer. The service was configured to skip when the drive was unavailable.

Enabling that timer wasn’t the last piece of evidence. The November 25 upgrade receipt recorded an automatic run at 04:17 and a clean repository check. That showed the scheduled path had actually run, beyond the earlier manual service test.

CyberBiota_Ark gave this upgrade an external encrypted recovery copy and a verified selective restore. It remains an attached USB backup rather than an offsite or continuously offline copy. Full host-loss recovery still needs replacement hardware, the separately held key, the missing application coverage, and a wider recovery exercise.
