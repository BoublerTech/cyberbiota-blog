Storage & recovery

Taking a backup off the laptop

I added an encrypted repository to an existing USB drive, restored selected files, and checked the overnight job.

By BoublerTechNovember 25, 20263 min read

The first backup question in the CyberBiota3.5 audit was where the successful jobs were writing. The verified copies were on the same laptop that ran the lab.

That left me with a recovery gap. A local archive could help after a bad edit, but I didn’t have a verified copy outside the machine. I approved adding an encrypted Restic repository to the external USB drive under the name CyberBiota_Ark.

The drive already had my files on it

This wasn’t an empty disk waiting to be formatted. The job created its own repository directory and left the existing files alone.

Its scope was specific: the new 3.5 project records, selected Compose configuration, scripts, and the latest verified daily OpenClaw archive. Staging and selected sensitive or runtime files were excluded. It was a recovery copy for that material, rather than a full image of the laptop or every application’s data.

Restic encrypted the repository. The job used the established credential arrangement without printing values in its receipts. I also needed a usable copy of the repository password outside the Dell. The encrypted files would be little use on replacement hardware if the only decryption key disappeared with the host.

Test the missing drive before the successful backup

During the power and SSD work, the USB drive was disconnected. That gave the mount guard a useful test.

A missing mount can leave an ordinary directory at the expected location. A backup job that writes into it can fill the internal disk while looking as though it is using external storage. This script returned its designated skip code when the drive was absent and didn’t write into the root filesystem. The service checked the mountpoint and the expected backup directory before proceeding.

Once the drive was reconnected, the recorded backup processed about 355 MiB across 13,015 files. It exited successfully, and restic check reported no errors. A separate start through the systemd service also passed under its CPU and memory limits.

Restore something from the external copy

The restore test brought two selected project files back from the USB repository into a private staging directory on the data SSD. Their SHA-256 hashes matched the originals. The selective restore took 1.07 seconds, after which the temporary directory was removed.

That established that those files could be recovered from the encrypted external copy. The timing belongs to that two-file exercise. It doesn’t describe how long it would take to rebuild CyberBiota or restore its applications.

The database restore went further by restoring a dump into an isolated PostgreSQL engine. I kept the two results separate because a matching file and a usable database answer different questions.

Watch the overnight job run

The USB timer was set for 04:15 with up to two minutes of randomized delay and persistent scheduling. It was configured to skip when the drive wasn’t available.

The November 25 upgrade receipt recorded an automatic run at 04:17 and a clean repository check. That was the scheduled path actually running, beyond the manual service test.

CyberBiota_Ark now gave this upgrade an external encrypted copy, a selective restore receipt, and an unattended-run receipt. It was still an attached USB drive. Offsite protection, complete application coverage, and recovery onto replacement hardware remained separate work.
