Giving the agents separate jobs

The new role structure divided operations into leads and specialists, with explicit limits on tools and delegation.

By BoublerTechNovember 25, 20263 min read

Work covered: November 23–24, 2026

CyberBiota3 already had 14 agent IDs when I started this upgrade. The coordinator was connected to Telegram, and the older roles had existing workflows. Replacing their configuration in one step would have made it harder to tell what broke.

The new role structure was built offline first. It used 32 identities, each with a defined job and an explicit delegation path. Only main, the coordinator, shared its name with the old structure.

Divide the work without loading more models

The departmental roles covered security operations, network operations, help desk, Linux, Docker, databases, the AI platform, and backup and recovery. Those eight departments contained 30 roles. The coordinator and independent governance role brought the total to 32.

Ten were called core identities, with 22 specialists available on demand. Core meant addressable; it didn’t start a continuous model process or authorize a new heartbeat. The RTX 2070 still had 8 GiB of VRAM, and local reasoning started serially.

A database performance question had this intended route:

Owner → main → dba-lead → dba-performance

The coordinator could reach department leads. Leads could reach their own registered specialists. Specialists had no children, and governance could review evidence without approving a change.

The candidate required explicit agent IDs and allowed two delegation edges below main. Structural checks looked for cycles, orphaned routes, and paths beyond that limit. The three new database-role IDs were checked for collisions with the existing registry before being added.

Give the restrictions something to run on

Separate workspaces helped organize the roles, but the design also needed a runtime boundary. Each new role had its own state directory and a Docker sandbox, with read-only workspace access, no sandbox network, a read-only root filesystem, and dropped capabilities.

The recorded production settings for the 31 new roles included:

{
  "mode": "all",
  "scope": "agent",
  "workspaceAccess": "ro",
  "docker": {
    "network": "none",
    "readOnlyRoot": true,
    "capDrop": ["ALL"],
    "memory": "512m",
    "cpus": 1
  }
}

These sandbox settings worked alongside per-role rules denying shell execution and modifying tools. Later, a live container inspection checked the filesystem, network, capabilities, and resource limits.

Add the new roles beside the legacy ones

The production cutover added 31 entries and reused main as the coordinator for the new lead-only routes. The 13 other legacy IDs stayed in place. That left 45 registered IDs: 32 in the 3.5 structure, including main, plus the 13 preserved roles.

The count describes the registry. It doesn’t mean 45 workers were reasoning at once or that the preserved roles acquired the new roles’ complete sandbox policy.

Check a refusal as well as a successful route

The offline candidate passed OpenClaw’s schema validator and the checks for IDs, tool restrictions, and delegation edges. The staging pilot then tested things a schema couldn’t establish: a role reading another workspace, reaching a credential store, or skipping a department lead.

Those attempts were denied. The allowed route from the coordinator to noc-lead succeeded. Getting that successful delegation took another change, though: the local model’s multi-step test failed, and the working pilot used a cloud coordinator with local Qwen3 specialists.
