CyberBiota3.5 · Retrospective

Thirty-two roles on one home lab

The upgrade divided operations into leads and specialists, then tested who could read, delegate, and execute.

Events: November 23–24, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

The live CyberBiota3 configuration already had 14 agent IDs when we began the upgrade. That made replacing it a migration problem: the Telegram-bound coordinator and the older workflows still had jobs to do.

I approved designing the new structure offline first. It used 32 roles, with exact IDs and explicit delegation paths. Only the existing coordinator, main, shared its name with the new structure.

Give each role a bounded job

The design grouped work into eight departments: security operations, network operations, help desk, Linux, Docker, databases, the AI platform, and backup and recovery. Together they contained 30 roles. The coordinator and an independent governance role brought the total to 32.

The split was ten core identities and 22 on-demand specialists. “Core” meant an identity the system could address. It didn’t mean a continuously running model or a new heartbeat job.

A database question illustrates the intended route:

Owner
  → main
    → dba-lead
      → dba-performance

The coordinator could delegate to a department lead. A lead could delegate to its registered specialists. Specialists couldn’t spawn their own teams. Governance had no children and could review evidence without approving a change.

That structure put a limit on how far a request could spread. The candidate required explicit agent IDs, allowed two delegation edges below the coordinator, and started with one concurrent run. A graph check looked for unreachable roles, cycles, and paths that exceeded the depth limit.

A workspace isn’t the whole boundary

Each new role had a separate workspace and state directory. The candidate also specified a Docker sandbox, read-only workspace access, no sandbox network, a read-only root filesystem, dropped capabilities, and explicit denial of shell and modifying tools.

The production registration later recorded these settings for the 31 newly added roles:

{
  "mode": "all",
  "scope": "agent",
  "workspaceAccess": "ro",
  "docker": {
    "network": "none",
    "readOnlyRoot": true,
    "capDrop": ["ALL"],
    "memory": "512m",
    "cpus": 1
  }
}

This is an excerpt of the recorded configuration, not a complete deployable file. The per-role tool rules were another part of the restriction. A later live test inspected a running sandbox to check that the network, root-filesystem, capability, CPU, and memory settings were actually applied.

Keep the migration count honest

The three database IDs were checked for collisions and explicitly ratified. The older roles were mapped in the design, but that mapping didn’t authorize deleting them.

At production cutover, 31 new roles were added beside the existing configuration. main became the shared coordinator for the new delegation paths, and the 13 other legacy roles were preserved. The live registry therefore contained 45 IDs: 32 belonging to the 3.5 structure, including main, plus 13 preserved legacy IDs.

That count doesn’t show 45 active workers, nor does it establish identical permissions across the old and new roles. The new sandbox settings were recorded per new role; the legacy configuration was deliberately preserved.

Test the rules after the configuration passes

The offline candidate passed OpenClaw’s schema validator and the project checks for role counts, delegation edges, and forbidden tools. Runtime tests then asked different questions: could a role read another workspace, access the credential store, or skip the hierarchy?

Those attempts were denied in the staging pilot. The allowed coordinator-to-lead route succeeded. The next post covers the complication behind that success: the local model didn’t complete the multi-step delegation task, and the working pilot used a cloud coordinator with local specialists.
