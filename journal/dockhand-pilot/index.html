Trying Dockhand before replacing Portainer

I compared inventory, logs, and resource readings with both tools available before making a cutover decision.

By BoublerTechNovember 24, 20262 min read

Portainer was already there when I tried Dockhand. I wanted to see how the other tool felt for the work I usually need a management screen to do: find a container, watch its logs and check how much of the host it is using. I kept Portainer available and left the Compose deployment files in charge of configuration. That way I could compare the interfaces without having to commit to a migration.

The November 11 report is a record of what I was able to check on the first day.

Task Observation
Find what’s running Dockhand and Docker listed the same 97 containers, of which 72 were running.
Follow a container’s output A live log stream returned output from the selected container.
Check resource use Sampled memory matched Docker. CPU readings differed slightly between polls.
Try the inventory without signing in The request returned HTTP 401 after native app authentication was configured.

The report also inspected the bind mount used to reach Docker. That established the mount setting. It did not show which Docker API operations the app was authorized to make. That question needs a separate check before I can describe the permanent setup as limited to inspection.

The pilot started a planned observation period. The report I used doesn’t include the result of that period or a completed retirement of Portainer. The useful result I can show is narrower: the everyday inspection tasks worked in the comparison, and I still had the existing interface if the new one stopped being useful.
