What I wanted from CyberBiota3.5

The next step for a home lab built to run my own apps and keep my own data—and the machine I had to build it on.

By BoublerTechNovember 25, 20263 min read

I wanted my first home lab to use open-source technology to host my own apps and data. That goal started with AriseOne. CyberBiota 1 and 2 gave me different versions to try, and CyberBiota3 was the fresh start that brought those earlier lessons together.

For CyberBiota3.5, the next step was to improve the machine and operating tools around the services already running. The work started with a plan on November 22 and reached the live coordinator cutover on November 25.

A bigger plan, on the same laptop

The plan had two connected aims. OpenClaw would coordinate work on the home lab. Addie 3 would bring together personal knowledge, planning, research, and selected actions. It covered the interfaces, model routes, retrieval, tools, identity, automation, monitoring, and recovery around that assistant.

The following days delivered a narrower set of changes I can trace: host repairs, the operations roles, subscription-backed inference, read-only and draft adapters, recovery tests, and the gateway cutovers. Those records don’t establish that the complete personal-assistant and second-brain plan was implemented.

The machine carrying the work was the existing Dell G7 7700: a six-core, twelve-thread i7, about 30 GiB of usable RAM, and an RTX 2070 with 8 GiB of VRAM. It already hosted applications, databases, monitoring, and local inference.

Find the problems before adding to them

The first audit counted 98 containers: 70 running, 25 exited, two created, and one restarting. Authelia was the restarting service. Its failure also broke the authenticated proxy test even though OpenClaw itself answered its health check.

The smaller system SSD was 87% full. The larger data SSD had about 1.2 TiB free. Most running containers lacked CPU or memory limits, and the repository backup job had failed on its last recorded run.

The paperwork needed corrections too. The running monitoring backend was VictoriaMetrics, with vmalert, Alertmanager, Grafana, Loki, Alloy, and Blackbox Exporter. NetBox and CrowdSec were already deployed. An older proposal’s component list wasn’t a reason to install another copy of work the lab could already do.

Those findings set the first jobs: repair the host, recover space, and check the backups.

Keep the build inside its resource budget

I ruled out the second laptop after its inspection. It had a two-core, four-thread processor, about 14 GiB of RAM, Wi-Fi connectivity, and no available KVM device. This project stayed on the Dell.

I also confirmed Qwen3 as the local model. The first GPU snapshot showed it using about 6.6 GiB of the available 8 GiB. That left little room for another GPU consumer and made serial local inference a deliberate limit.

The agent design divided responsibilities into 32 identities. It didn’t load 32 models into memory. The early candidate ran beside production with separate state, an offline configuration, and a loopback-only staging gateway. The existing Telegram binding and legacy workflows stayed available during the tests.

Carry the tested pieces into production

By November 24, the new role entries had been added to the live configuration. On November 25, the runtime upgrade and cloud coordinator were in place. An allowed cloud-to-local delegation succeeded, while a request that skipped its department lead was denied.

The same project also produced an external encrypted backup, a selective USB restore, a functional database restore, and controlled adapter and incident tests. Automatic production remediation remained disabled, heavy security additions were deferred, and the observation period was still running.

Each of those changes has its own entry in the journal. They explain what was tried and what the checks showed, including the failures that changed the implementation. That’s the part of CyberBiota3.5 I can describe from this round of work.
