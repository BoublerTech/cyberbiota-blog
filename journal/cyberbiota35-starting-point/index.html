CyberBiota3.5 started with the lab I already had

The November upgrade began with an audit of a working home lab: one laptop, crowded storage, a local model, and several problems to fix before building on it.

Events: November 22–25, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

I started home labbing because I wanted to use open-source technology to host my own apps and keep my own data. AriseOne was the beginning. CyberBiota 1 and 2 gave me room to try different versions of the lab. CyberBiota3 brought those earlier lessons together.

CyberBiota3.5 builds on that same lab. The work recorded here happened over November 23–25, 2026: checking the host, repairing existing faults, testing a new agent structure, improving recovery, and putting the approved changes into production. I worked with coding agents on the implementation. The decisions, approvals, test results, and failures were recorded as we went.

The plan reached beyond the agent registry

The November 22 plan had two connected aims. OpenClaw would coordinate work on the home lab, while Addie 3 would bring together personal knowledge, planning, research, and selected actions. It covered the frontends, model routes, retrieval and memory, tools, identity, automation, monitoring, and recovery around that assistant.

The implementation records from the following days are more specific: host repairs, the operations roles, subscription-backed inference, read-only and draft adapters, recovery tests, and the live gateway changes. They don’t establish that the whole personal-assistant and second-brain plan was delivered. This series follows the work we can trace through those records; the broader plan remains context for where it is meant to lead.

Start by finding out what is actually running

The first inspection found 98 containers: 70 running, 25 exited, two created, and one restarting. That last one was Authelia, the authentication service. Its crash loop was also making the authenticated proxy check fail, even though OpenClaw’s own health endpoint still responded.

The machine was a Dell G7 7700 with a six-core, twelve-thread i7, about 30 GiB of usable RAM, and an RTX 2070 with 8 GiB of VRAM. It already ran the apps, databases, monitoring, and local inference. There wasn’t an empty server waiting for the new design.

The smaller system SSD was 87% full. The larger data SSD had about 1.2 TiB free. Fifty-three of the 70 running containers had no memory limit; 55 had no CPU limit. The repository backup service had failed on its last recorded run. Those findings determined the first changes.

The audit also corrected the paperwork. The monitoring backend was VictoriaMetrics, with vmalert, Alertmanager, Grafana, Loki, Alloy, and Blackbox Exporter. We didn’t need to install another monitoring stack just because an older plan named one. NetBox and CrowdSec were already running too.

Keep the upgrade inside this machine’s limits

I ruled out adding the second laptop to this build. Its inspection showed a two-core, four-thread processor, about 14 GiB of RAM, Wi-Fi connectivity, and no available KVM device. The approved project stayed on the Dell.

I also confirmed Qwen3 as the local model. An earlier proposal referred to a model that wasn’t installed. Ollama was actually serving qwen3:8b, and the first GPU snapshot showed it using about 6.6 GiB of the 8 GiB available. That made concurrent local inference a real capacity question.

The new design separated the work into 32 named roles across operations, security, databases, recovery, and the AI platform, with a coordinator and an independent governance role. These were identities with different permissions. They weren’t 32 models loaded into memory. Local reasoning started serially, and specialists were intended to run when needed.

Build beside production, then cross over deliberately

The early phases used separate state directories, an offline candidate configuration, and a loopback-only staging gateway. The existing OpenClaw gateway, Telegram binding, and legacy agents stayed in place while we tested.

By November 24, the new roles had been added to production. On November 25, OpenClaw had been upgraded and the live coordinator was using the approved OpenAI subscription route while the other roles stayed on local Qwen3. An allowed delegation succeeded; an attempt to skip the department lead was denied.

There is still a difference between reaching that point and finishing every part of the larger vision. The adapter suite was tested separately from the live gateway routing. Automatic production remediation remained disabled. Heavy security platforms were deferred, and the seven-day observation period was still underway when I wrote this.

The posts that follow trace the actual work: the clock and container repairs, the external backup, the failed local delegation test, the monitoring interfaces, the database restore, the incident drills, and the final cutover. That is the November upgrade I can show from the records.
