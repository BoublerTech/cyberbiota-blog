CyberBiota3.5 · Retrospective

Teaching the new tools to read the lab

The monitoring work reused VictoriaMetrics, Loki, NetBox, and existing probes, then added bounded Python adapters for specific operational questions.

Events: November 23–24, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

CyberBiota already had monitoring before the 3.5 upgrade. The discovery pass found VictoriaMetrics, vmalert, Alertmanager, Grafana, Loki, Alloy, and Blackbox Exporter running. NetBox held inventory, and AdGuard handled DNS.

The new work was to give the project small, testable ways to read those systems. We didn’t add another polling stack.

Ask a specific question

The first Python adapter set covered host and container health, bounded logs, network metrics, DNS and TLS checks, database health, backup status, restore evidence, and draft tickets.

Instead of taking an arbitrary monitoring query, network_health_query accepted a named query template. The probe helper accepted approved targets. The database helper exposed fixed health views rather than arbitrary SQL. The container view omitted environment variables.

That made the interfaces useful to test. An argument either selected a supported operation or was rejected. The tests included arbitrary URLs, SQL text, shell fragments, and free-form metric queries; those inputs were denied.

The common adapter code also applied output limits and redaction. It capped responses at 64 KiB, recorded calls in a restricted audit log, and returned unavailable when a backend couldn’t be reached. An unavailable result had to remain visible to the caller.

Follow one failed probe through to a draft

The first monitoring drill used a deliberately closed local port. Blackbox Exporter reported probe_success=0. The adapter created a draft ticket and recorded that no external notification had been sent.

Replaying the same idempotency key returned a deduplicated result. A check against the working target then returned probe_success=1.

That sequence tested failure detection, draft creation, repeat handling, and the contrasting healthy probe. It didn’t simulate a real customer outage or prove that an agent repaired a service. Nothing was automatically restarted.

The live integration checks also looked for fresh telemetry, read an Alertmanager summary, retrieved a small bounded log sample, and checked selected host, container, database, and backup metadata. The first combined set passed 11 tests.

Compare inventory with what the host reports

The next stage added NetBox inventory queries and a redacted configuration diff. The inventory reconciliation compared the host’s passively observed addresses with a sample from NetBox. Both observed host addresses were represented in that sample.

That result was about this host and that inventory sample. It didn’t show that every device on the home network was accurately inventoried.

The diff adapter read only approved configuration files. Tests rejected traversal into other paths, secret-file requests, invalid revisions, and unauthorized role IDs. The purpose was to explain a configuration change without returning a raw checkout full of unrelated settings.

There was also a documentation mismatch worth resolving before writing this post: one phase report described a broader set of authorized NOC names than the implementation’s role allowlist. The shared adapter code has the narrower list. I haven’t treated the longer report table as proof that those extra roles have access.

Leave network visibility gaps visible

The Dell was connected over Wi-Fi. There was no authorized switch-mirror feed, no live packet sensor, and no approved set of switch polling targets in this work.

We deferred Zabbix, Oxidized, SmokePing, and continuous flow tooling because the existing stack covered the approved questions or the hardware and network setup didn’t justify the addition.

The Python tests reached live backends. The later gateway tests proved selected role routing and sandbox behavior. Those are separate results: this work doesn’t yet demonstrate a real Telegram incident using every adapter end to end. The next step is to collect that evidence during actual use, without changing the meaning of the tests we already have.
