Making the monitoring answer useful questions

I reused VictoriaMetrics, Loki, and NetBox, then tested small interfaces for probes, inventory, logs, and configuration changes.

By BoublerTechNovember 25, 20263 min read

The CyberBiota3.5 audit found a monitoring stack already doing work: VictoriaMetrics, vmalert, Alertmanager, Grafana, Loki, Alloy, and Blackbox Exporter. NetBox held inventory, and AdGuard handled DNS.

I didn’t need another monitoring installation to answer the first operational questions. The project added small Python adapters to read those existing systems and return bounded results.

Give each query a shape

The first adapter set covered host and container health, logs, network metrics, DNS and TLS probes, database health, backup status, restore evidence, and draft tickets.

A network-health call selected a named query template. The probe helper accepted approved targets. The database helper exposed fixed health views, and the container view left out environment variables. Those choices reduced how much arbitrary input could reach the backend.

The negative tests tried URLs outside the approved targets, SQL text, shell fragments, and free-form metric queries. They were denied. Shared code applied redaction, capped output at 64 KiB, and recorded calls in a restricted audit log. An unreachable backend returned unavailable rather than a made-up healthy result.

These checks exercised the adapters under tested inputs. They weren’t a substitute for an authenticated production tool boundary.

Follow a failed probe into a draft

The monitoring drill targeted a deliberately closed local port. Blackbox Exporter reported probe_success=0, and a draft ticket was created without sending an external notification.

Replaying the idempotency key returned a deduplicated result. Checking the working target then returned probe_success=1.

I could follow that small chain: failed probe, draft, duplicate handling, healthy comparison. There was no automatic restart or claim that an agent had repaired an outage.

Other checks read fresh telemetry, an Alertmanager summary, a bounded log sample, and selected host, container, database, and backup metadata. The first combined set passed 11 tests against the existing services.

Compare the inventory with the host

The next stage added NetBox inventory queries and a redacted Git configuration diff. Passive observation of the host’s addresses was compared with a sample from NetBox. Both observed host addresses were represented in that sample.

That was a useful reconciliation for this machine. It didn’t establish that every device on the home network was inventoried correctly.

The configuration helper read an explicit set of approved files. Tests rejected traversal into other paths, secret-file requests, invalid revisions, and unauthorized role IDs. That made it possible to inspect a relevant change without handing a model the whole checkout.

The report and code weren’t perfectly aligned here. One validation table listed a broader set of NOC roles than the shared implementation allowed. I used the narrower code allowlist when describing the result; the larger table didn’t prove those other roles had access.

Keep the visibility limits in view

The laptop was on Wi-Fi. There was no authorized switch-mirror feed or live packet sensor in this work. Zabbix, Oxidized, SmokePing, and continuous flow tooling stayed deferred because the existing tools covered the approved questions or there wasn’t a justified source and resource budget for the addition.

The Python checks reached live backends. The separate gateway tests checked selected role routing and sandbox behavior. I still needed a real request through Telegram and the new tools to establish the complete user path. For this stage, I had tested interfaces I could use for that next check, with their limits recorded.
