Why CyberBiota 2 moved to bare-metal Ubuntu

I tried virtual gateways and moved a fleet of guests before deciding to run Docker directly on Ubuntu. Here is what that removed and what it left me responsible for.

Events: March 6 to May 2026Evidence: Network and access notes, April change log and transition summaryEntry date: November 24, 2026

The last night of the Proxmox build involved moving Linux guests to a new network, restarting them, and updating the reverse proxy so it knew where to find their services. The log says the monitoring UI remained reachable and the proxy got responses from the backends it checked. The next morning, I was starting over with Ubuntu.

That decision had a few months of experiments behind it. One March note records a failed attempt to restore OPNsense. Another describes a VyOS attempt that had problems. A later summary gives a different account of the gateway’s condition, so I can’t make a clean timeline of every working configuration. By April 6, the log does say the separate gateway experiments were being set aside in favor of Proxmox’s own network layer.

The hardest part of a network change can be getting back in when it goes wrong. The March 14 notes describe losing SSH access after a change and having limited physical recovery options on a laptop usually run without a local console. A service responding through the proxy would not help if I couldn’t reach the host to undo the change.

The April 7 rebuild

The next build, CyberBiota 2, ran Ubuntu and Docker on the hardware. The installation record names Ubuntu 25.10. It describes a separate NVMe drive for persistent application data and local model storage, and records the NVIDIA driver seeing the GPU. The reasons in the transition notes were practical: memory pressure, competing workloads, and the repeated friction of getting commands and services through nested layers.

Before After
Proxmox host with networked guests Ubuntu on the hardware, with Docker running on the host
Storage organized through the virtualization layout A separate NVMe drive allocated to persistent app and model data
Hardware and service checks spread across host and guests The native host could see the GPU in its own driver check

It was a simpler layout to describe. It also concentrated more responsibility on the one host: storage, app permissions, backups and the path back into a machine that was normally headless. The April notes don’t give me enough measurements to claim a performance improvement, or a full restore list to say every application’s data survived. Later papers refer to Ubuntu 26.04 and don’t settle whether that was an upgrade or another reinstall.

For the thing I wanted out of my lab, hosting my own apps and data, the useful part of this story is what moved where. I could keep using containers. I no longer had to put a virtualized host between that container work and every part of the machine.
