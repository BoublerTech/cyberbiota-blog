Why CyberBiota 2 moved to bare-metal Ubuntu

A final Proxmox network migration was followed the next morning by a fresh Ubuntu install. That choice changed the lab’s network, storage, and hardware boundaries.

Events: March 6 to May 2026Evidence: Network and access notes, April change log and transition summaryEntry date: November 24, 2026

On April 6 the log records a fleet of Proxmox guests being moved onto a native software-defined network. The virtual gateway work had already taken several turns. The March records describe a failed OPNsense restoration and an unreliable VyOS installation attempt. A later summary describes the gateway differently. I can show the attempts and the April decision to leave those separate gateways behind. I can’t establish every intermediate working state from the records.

Access had already become part of the problem. The March 14 notes describe an SSH lockout after changes to the management network and access conditions. They also describe how little room there was to recover on a laptop being operated without a local console in normal use. Having a path from the proxy to the application would not solve that problem. The person operating the host still needed a way back in if a network change failed.

The last Proxmox evening shows the amount of work a network move could create. The log records changing guest network configuration, restarting the guests, and updating the reverse proxy’s backend targets. Uptime Kuma remained reachable during the recorded check, and the proxy was able to reach checked backends. That gave some confidence in the change. It did not establish that every application workflow was available to every client.

The next morning, April 7, the transition record calls for replacing that virtualization layout with a clean Ubuntu 25.10 installation. Docker would run on the host. A separate NVMe drive was set aside for persistent application data and model storage. The record reports that Ubuntu detected the GPU and that the driver check passed. The decision notes cite memory pressure, scheduling constraints, and the complexity of passing shell commands through several systems. Those are the recorded reasons for reducing the number of layers. I don’t have a before-and-after benchmark that quantifies their effect.

This was CyberBiota 2. It was a fresh installation with a different failure model. It moved more responsibility onto a single host for storage, permissions, and recovery. The records identify the new layout and the original Ubuntu release. They do not supply a verified migration list for every application and volume. Later records refer to Ubuntu 26.04. Whether that change was an upgrade or another reinstall is still open. I can say what the rebuild was designed to simplify and what its first checks showed, while keeping each of those unknowns attached to the transition.

Reading note

Historical results describe what the records showed at the time. They are not a live status check.
