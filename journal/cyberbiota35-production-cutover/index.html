CyberBiota3.5 · Retrospective

Putting CyberBiota3.5 into production

The final changes added the new roles, upgraded OpenClaw, and proved a live cloud-to-local delegation. The observation period and recovery gaps remained open.

Events: November 24–25, 2026Evidence: Project records reviewed through November 25, 2026Entry date: November 25, 2026

By late November 24, the offline design, staging pilot, adapter tests, and restore exercises had their validation records. The operating handoff had also been written. It still described the production cutover as future work.

The project then continued through separately approved changes. That sequence matters when reading the files: the later cutover receipts supersede the handoff’s statement about production still being untouched.

Add the new roles without removing the old workflows

The first cutover saved a restricted pre-change configuration copy, checked its hash, and ran the external USB backup. The merged configuration passed OpenClaw’s schema validator before it replaced the live file.

We added 31 role entries, each with its own workspace and state directory. Their per-role settings included a Docker sandbox, no sandbox network, read-only root and workspace access, dropped capabilities, resource limits, and denied shell execution.

The existing main ID was wired to the eight department leads. Thirteen other legacy IDs, the Telegram binding, the documentation heartbeat, and the existing MCP server configuration were preserved. That made 45 registered IDs in total.

The gateway restart took about 35 seconds through plugin and channel startup. The direct health response and reliability monitor passed afterward. A live governance turn identified its role and refused the requested shell and host-file access. Inspecting its actual Docker container confirmed the recorded network, filesystem, capability, memory, and CPU restrictions.

The new per-role restrictions don’t establish that every legacy role or the preserved coordinator inherited the complete candidate policy. This was an additive cutover with targeted verification, not a clean replacement of all existing permissions.

Upgrade the runtime as a separate change

The next approved packet upgraded OpenClaw from 2026.10.4 to 2026.11.9. Beforehand, the daily OpenClaw backup and external USB copy had successful receipts.

Two admission blockers needed attention. An unused development symlink caused the candidate snapshot to be rejected; its target was recorded before removing the link. The expected policy-attestation hash also needed reconciliation with the verified post-cutover state. The recorded policy check passed all 68 checks before the upgrade proceeded.

Afterward, the installed version, live health, schema validation, reliability monitor, and a sandboxed governance turn were checked again. The 37-test adapter suite passed. The newer model entries appeared in the catalog.

One host result stayed separate: the daily AIDE file-integrity service reported failure after the approved changes. The upgrade receipt left that for an explicit baseline-review decision. It didn’t reinitialize the integrity database simply to clear the failure, and I can’t call that later checkpoint entirely clean.

Put the hybrid coordinator on the live route

I completed the official device-code authorization for the production coordinator. We didn’t copy the staging credentials into it.

main was configured for openai/gpt-6.2-sol through OpenClaw’s built-in runtime, with an empty fallback list. The default remained local ollama/qwen3:8b for the other 44 roles.

The smoke test recorded the expected cloud model and no fallback. The credential checks found no OAuth duplication in the 31 new role directories and no OpenAI API-key environment variable in the gateway process.

The decisive routing check used the live gateway: main delegated to local noc-lead in a restricted sandbox. A direct attempt to reach soc-tier1 was denied. Health and readiness passed, and the adapter suite passed again. The owner accepted these two final change packets on November 25.

Where this leaves the lab

The records show a production upgrade, an external backup with a selective restore, a functional database restore, new role boundaries, tested adapters, and a live hybrid delegation path. They don’t yet show every adapter used through a real Telegram request, a complete application recovery, or enabled production remediation.

The project scheduled a seven-day observation window from November 24 to December 1. As of this November 25 entry, that period hasn’t elapsed. The final acceptance needs the daily backup receipts and stability evidence, with material regressions investigated and the affected observation period reset where required.

The remaining list also includes the AIDE review, incomplete database dump coverage, no demonstrated WAL-based point-in-time recovery, the separately held recovery key, and the pending desktop-agent permission review. There is still one host and no failover.

That is the current stopping point for this series. The next post should come from what the lab actually does during the observation period: the scheduled jobs, any failures, the fixes, and the eventual acceptance decision.
